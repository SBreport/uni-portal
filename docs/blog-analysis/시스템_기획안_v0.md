## 1. 목표 서비스 정의

**블로그 성과 분석 시스템** — 노션 원본에서 내려받은 DB 스냅샷을 입력하면,
가시성 좋은 대시보드로 가공해 현황을 진단하는 내부 데이터 분석 도구.

핵심 질문 (사용자 요구 기준):

- 지점별 담당자가 누구인가
- 어느 기간에 어떤 성과(노출/실패)를 냈는가
- 성과가 낮은 지점들의 공통 특징은 무엇인가
- 원하는 조건(기간·지점·그룹·담당자·원고유형)을 필터로 조합해 볼 수 있는가

별도 Git repo로 분리, uni-portal의 일부 기능은 추출해 재사용.

## 3. 현재 상태의 문제점 (진단)

### P1. 규칙이 코드에 갇혀 있다 — 가장 큰 문제
지점 별칭·기준표·임계값·날짜 범위가 전부 `.mjs` 스크립트에 하드코딩.
- generate_report.mjs: 별칭 38개 + 기준표 31지점 하드코딩
- generate_author_audit.mjs: 별칭 ~95개 하드코딩 (서로 불일치)
- bioadd: 대상 7지점 하드코딩 / optimal_blog: 월 목록 하드코딩

→ 새 분석마다 규칙을 복붙·재작성. 별칭 맵이 스크립트마다 달라 같은 지점이 프로젝트마다 다르게 정규화될 수 있음.

### P2. 프로젝트마다 스크립트를 새로 짠다
4개 프로젝트 합계 ~3,765줄, 순수 Node.js. rank_status 계산, 실패율, 상태 색상 로직이 4번 중복 구현됨. 재사용 모듈 0개.

### P3. 대시보드가 일회성 정적 산출물
HTML은 잘 만들어졌지만 필터 축이 고정(제작 시점에 정한 탭·그룹만). "내가 필요한 정보를 필터로 넣어서 본다"는 목표와 거리 있음.

### P4. 담당자 축은 데이터가 먼저다
manager 프로젝트 감사 결과: sub_manager 컬럼 부실, 기준표는 6월 시점 스냅샷뿐, 1~5월 담당 이력 없음. **시스템을 만들어도 담당자별 성과는 기준표 이력화 전까지 부정확.** (감사 단계에서 성과 분석 보류된 상태 — 올바른 판단이었음)

### P5. uni-portal 안에 있어 독립 진화 불가
분석 산출물이 서비스 repo의 docs/에 섞여 있음. 42MB. 별도 repo 목표와 어긋남.

### P6. 수동 검증
row 수·해시·최신 발행일 확인이 문서 속 수동 체크리스트. 자동화 안 됨.

## 4. 권장 아키텍처 (최소 구성)

핵심 판단: **데이터 규모(blog_posts 21,512행)가 작다. 서버 불필요.**
전체 데이터를 JSON으로 embed한 정적 HTML + 클라이언트 JS 필터로 목표 기능 전부 구현 가능.
서버(업로드 UI, 다인 사용, 권한)는 필요해질 때 Phase 4로.

```
blog-analysis-system/            ← 새 Git repo (SoT)
├── config/                      ← P1 해결: 규칙 전부 외부화
│   ├── branch_aliases.csv       (별칭 → 정규 지점명, 4개 스크립트 맵 통합)
│   ├── branch_reference.csv     (지점 마스터: 과목, 운영그룹, 활성여부)
│   ├── manager_history.csv      (지점·기간별 담당자 — P4 해결의 그릇)
│   └── thresholds.json          (위험 70/50/35, rank 버킷, 상태 색)
├── standards/                   ← uni-portal에서 이동 (기준 문서가 규칙의 원본)
├── snapshots/                   ← 스냅샷 보관 (기존 db-snapshots 역할)
│   └── {날짜}/blog_snapshot_*.db + meta.md (해시·row수 자동 기록)
├── src/
│   ├── load.mjs                 (sqlite3 추출 — 기존 export_target_detail 일반화)
│   ├── normalize.mjs            (branch_link + enrich 포팅, config 참조)
│   ├── metrics.mjs              (rank_status·실패율·위험등급 — 단일 구현)
│   └── build_dashboard.mjs      (HTML 생성 — 기존 보고서 패턴 재사용)
├── dist/
│   └── dashboard.html           (전 데이터 embed, 자유 필터)
└── projects/                    (일회성 심층 분석은 기존 방식 유지)
```

기술 스택: **순수 Node.js 유지** (npm 의존성 0 관행 유지, sqlite3 CLI 호출). 이미 검증된 방식.

### uni-portal에서 추출/재사용할 것

| 대상 | 방법 |
|---|---|
| `blog/branch_link.py`의 매핑 규칙 | 로직을 JS로 포팅 + 특례 맵은 config CSV로 (Python 의존 제거) |
| `blog/enrich.py`의 정규화 규칙 | 동일 |
| `standards/` 문서 3종 | 새 repo로 이동, uni-portal에는 링크만 |
| `GET /blog/download-snapshot.db` | uni-portal에 그대로 둠 — 입력 공급자 역할. 수정 불필요 |
| HTML 보고서 CSS/컴포넌트 패턴 | build_dashboard.mjs 템플릿으로 정리 |

uni-portal 코드 변경: **0** (스냅샷 엔드포인트 이미 존재). 결합은 스냅샷 파일 하나로만.

## 5. 유저 플로우 (v1)

```
[운영 웹] 관리자 → 데이터 로그 → 블로그 분석 DB 다운로드
    ↓ blog_snapshot_YYYYMMDD_HHMMSS.db
[새 repo] snapshots/에 복사 → node src/build.mjs snapshots/…/xxx.db
    ↓ 자동: 해시·row수·최신발행일 검증 기록 (P6 해결)
    ↓ 자동: 정규화 → 미매칭 지점 audit 리포트 (기존 unmatched_audit 관행 유지)
[산출] dist/dashboard.html 브라우저로 열기
    ↓
[대시보드]
  필터 바: 기간(월) · 운영그룹 · 지점 · 담당자 · 원고유형(일반/최적) · 계정
  ├─ KPI 카드: 발행건 / 실패수 / 실패율 / 미노출 / 상위10밖  (공통기준 §4 순서)
  ├─ 위험 지점 리스트: 위험/주의/관찰 등급 자동 분류 (공통기준 §8)
  ├─ 월별 추이 차트 (SVG, 기존 패턴)
  ├─ 지점 상세 테이블 (정렬·검색)
  └─ 저성과 지점 특징 뷰: 실패율 상위 지점의 공통 속성(과목·그룹·계정·담당자) 교차표
    ↓
[Git] 스냅샷 meta + config 변경 + 산출물 commit = 이력 SoT
```

## 8. 제외 기록 (검토했으나 채택 안 함)

- **FastAPI + Vue 웹앱으로 시작**: 데이터 2.1만 행, 사용자 1명 추정 → 정적 HTML로 충분. 서버는 유지비만 생김
- **노션 API 직접 연동**: uni-portal이 이미 Notion sync + 스냅샷 다운로드를 안정 운영 중. 중복 구현 불필요, 스냅샷 파일이 더 깨끗한 경계
- **기존 4 프로젝트 산출물 마이그레이션**: 완료 프로젝트는 당시 DB 기준 유지 원칙(DB관리기준 §7). 그대로 동결 보관
